## 1. Colab 자원 감사

공고문 p.4: *"일반적인 Google Colab 자원 범위에서 정상적으로 실행 가능하여야 하며, 실행환경의 자원 한계로 정상적인 평가가 어려운 경우 기술적 보완을 요청할 수 있음"*

무료 등급 **T4 (16GB VRAM, 시스템 RAM 12~13GB)** 를 하한으로 가정한다. 실제 평가환경 등급은 9/18 확인 항목이다.

### 1.1 F1 — VAE 왕복의 VRAM (가장 큰 위험)

**문제.** A1은 이미지를 VAE로 인코드→디코드해 재구성 오차를 본다. 그런데 우리 설계 원칙은 **리사이즈 금지**다. AI Hub 스마트팜 이미지는 1920×1080급이 흔하다.

VAE는 컨볼루션 스택이라 **activation 메모리가 해상도에 선형 비례**한다. 512² 기준으로 수백 MB면, 1920×1080은 그 약 8배다. 디코더 중간 레이어는 잠재의 8배 해상도 × 128~512 채널이라 여기서 수 GB가 잡힌다. **T4에서 OOM이 날 수 있고, 나지 않더라도 배치 크기가 1로 묶인다.**

**해결 — 타일 단위 왕복을 설계에 못박는다.**

```
원본 이미지
  → 겹침 있는 타일로 분할 (예: 512×512, overlap 64)
  → 타일마다 VAE 왕복 → 타일별 재구성 오차
  → 타일 오차를 top-k 풀링 (전역 평균 아님)
```

부수 효과가 두 개 있는데 둘 다 유리하다.
- **VRAM이 타일 크기로 고정된다** — 입력 해상도와 무관해진다
- **top-k 풀링이 유형 ①②에 유리하다** — 잠재 인페인팅으로 일부만 재생성된 이미지는 그 영역의 타일에서만 오차가 낮게 나온다. 전역 평균은 이 신호를 희석시킨다

> **이건 성능을 위해서도 원래 했어야 하는 것이다.** 자원 제약이 더 나은 설계를 강제한 경우다.

### 1.2 F3 — 분할 모델은 MobileSAM으로 고정

| | params | fp16 용량 | 이미지당 인코딩 (T4 추정) |
|---|---|---|---|
| SAM ViT-H | 636M | **1,272MB** | **~1초** |
| MobileSAM | 10M | 20MB | ~10ms |

SAM ViT-H는 **용량만으로 제출 한도를 위협**하고, 5,000장이면 인코딩만 80분 이상이다. **MobileSAM(Apache-2.0) 고정.** 품질이 부족하면 SAM2-tiny를 검토하되 용량을 먼저 잰다.

### 1.3 F4 — 제출 용량

| 구성 | 내역 | 합계 |
|---|---|---|
| **경량** | FerretNet 2MB + VAE 166MB + MobileSAM 20MB + DINOv2 ViT-B 172MB + A4 50MB + B1 60MB | **≈ 470MB** |
| 중량 | 위에서 SAM ViT-H(1,272MB) + CLIP ViT-L/14(856MB) 사용 | ≈ 2,400MB |

**CLIP ViT-L/14 하나가 856MB로 경량 구성 전체보다 크다.** A5 보조는 **DINOv2 ViT-B(172MB, Apache-2.0)** 로 간다. 성능 차이는 자체 검증으로 확인하되, 차이가 작으면 용량이 우선이다.

> 제출 총 용량 한도는 **9/18 확인 항목**이다. 확인 전까지 **경량 구성을 기본값**으로 두고 설계한다.

### 1.4 F5 — 축 B의 CPU 병목

B1(잎맥 그래프)은 GPU가 아니라 **CPU에서 도는 작업**이다 — 세선화(skeletonize) → 그래프 구축 → 네트워크 특징 계산. 순수 Python/scipy 구현이면 이미지당 0.5~2초가 나올 수 있다.

| 테스트 장수 | B1만의 소요 (추정) |
|---|---|
| 500장 | 4~17분 |
| 2,000장 | 17분~1.1시간 |
| 5,000장 | 42분~2.8시간 |

Colab 런타임 한도(무료 ~12시간, 유휴 90분 종료) 안이기는 하나 **다른 지표와 합치면 위험 구간에 들어간다.**

**대응**
- 잎맥 분석은 **마스크를 축소한 뒤** 수행한다 (여기서는 리사이즈가 해롭지 않다 — 저수준 흔적이 아니라 **위상 구조**를 보기 때문이다)
- 그래프 특징 계산을 벡터화하고, 이미지당 분석 잎 수에 상한을 둔다
- **B2(시설 구조물)는 OpenCV Hough·FFT라 훨씬 싸다.** 종 미확정 상태에서 B2를 먼저 만드는 결정이 자원 면에서도 옳다

## 2. 규정 감사

### 2.1 F2 — FLUX.1-dev 라이선스 (반드시 교체)

확인된 사실: **FLUX.1-dev는 비상업 라이선스이고, 그 제한이 모델 가중치뿐 아니라 생성된 출력물과 파생 모델에까지 미친다.** 반면 **FLUX.1-schnell은 Apache-2.0**으로 제한이 없다.

본 대회에서 이게 두 군데를 건드린다.

**(가) 학습 데이터 생성용으로 dev를 쓸 때**
공고문 p.5는 *"실제 활용한 학습데이터"* 제출을 요구하고, p.10은 주최·주관기관의 **무상·비독점 이용권**을 규정한다. dev 출력물을 학습 데이터로 제출하면 그 비상업 제한이 제출물에 따라붙는다. p.10이 열거한 용도(운영·평가·검증·시상·교육·홍보·**비영리** 성과확산)는 비상업이라 정면 충돌은 아니지만, **명백한 회색지대다.**

**(나) A1이 쓰는 VAE 가중치 — 이쪽이 더 직접적이다**
A1은 VAE를 **제출물에 포함**해야 한다(p.5, 예외 없음). **FLUX.1-dev의 VAE를 쓰면 비상업 제한이 붙은 가중치를 제출하게 된다.**

**조치**

| 용도 | 쓸 것 | 피할 것 |
|---|---|---|
| A1의 VAE 가중치 | **FLUX.1-schnell VAE (Apache-2.0)** + SD1.5/SDXL VAE (OpenRAIL-M) | FLUX.1-dev VAE |
| 플로우 매칭 계열 학습 데이터 생성 | **FLUX.1-schnell (Apache-2.0)** | FLUX.1-dev |

**단, 트레이드오프가 있다.** schnell은 4스텝 증류 모델이라 full-step인 dev와 흔적이 다르다(`06` §7). 플로우 매칭 계열을 schnell만으로 재현하면 "소수 스텝의 흔적"만 배우게 된다.

→ **대안: SD3.5-medium(Stability Community License, 학술·비상업 무료)을 full-step 플로우 매칭 소스로 추가한다.** 이용조건을 제출자료에 명시한다. dev를 굳이 쓰려면 **생성 이미지의 제출 의무 범위를 9/18에 먼저 확인**한다.

### 2.2 OpenRAIL-M 계열의 사용제한 조항

SD1.5/SDXL의 VAE는 CreativeML OpenRAIL-M 계열이다. **재배포는 허용되나 사용제한 조항이 함께 따라간다.** p.10의 이용권과 충돌하지는 않지만, `THIRD_PARTY_NOTICES.md`에 조항이 승계된다는 사실을 명시해야 한다.

가장 깨끗한 길은 **A1의 주 VAE를 Apache-2.0(FLUX schnell VAE)으로 두고 OpenRAIL 계열은 보조로** 쓰는 것이다.

### 2.3 축 B의 라이선스 — 고전 방법이 오히려 안전하다

잎맥 분할에 공개 사전학습 모델을 가져다 쓰면 라이선스를 확인해야 하는데, **식물 표현형 분야의 공개 코드는 라이선스가 불명확한 경우가 많다.** 그런데 우리에겐 라이선스 문제 자체가 없는 길이 있다.

| 방법 | 라이선스 | 비고 |
|---|---|---|
| **Frangi / ridge 필터 등 고전 혈관강조 기법** | **없음 (알고리즘)** | scikit-image·OpenCV로 구현. **1순위** |
| 자체 학습 U-Net | 자체 | AI Hub 실제 이미지로 학습 |
| 공개 잎맥 분할 모델 | **확인 필요** | 라이선스 불명이면 사용하지 않는다 |

**B2(시설 구조물)는 Hough 변환·FFT라 애초에 라이선스 대상이 아니다.** 축 B 전체를 라이선스 리스크 없이 구성할 수 있다.

### 2.4 F6 — 제출 후에는 브랜치를 뺄 수 없다 (절차 문제)

공고문 p.10: *"제출기한 이후에는 (…) 제출자료를 수정할 수 없으며"*, *"기술적 보완은 동일한 예측결과의 재현을 위한 실행환경·경로·설정 등의 수정에 한하며, 모델 구조·가중치·예측결과 등 성능에 영향을 미치는 변경은 허용하지 않음"*

**즉 `02` §4.6의 단계적 축소(A3 → A2 → B3)를 제출 후에 적용할 수 없다.** 지표를 빼는 것은 모델 구조 변경이고 예측결과가 바뀐다.

**조치**
- 자원 초과 여부를 **제출 전에** 판정하고, **한도 안에서 도는 구성으로 확정해 제출**한다
- 축소 순서는 "사후 대응책"이 아니라 **제출 전 의사결정 순서**로 문서에 기재한다
- 제출 직전 체크리스트에 **"Colab 무료 등급에서 테스트 규모 추론 완주 + 소요 시간 측정"** 을 필수 항목으로 둔다 (`01` §7에 이미 있음 — 이제 이것이 통과 조건이다)

### 2.5 나머지 규정 항목 — 문제 없음

| 항목 | 판정 | 근거 |
|---|---|---|
| 다단계 파이프라인(분할 → 지표 → 융합) | ✅ | p.4 *"모델 구조에는 별도의 제한을 두지 않음"* |
| 축 B를 실제 이미지만으로 학습 | ✅ | 외부 데이터 출처 명시(p.5)만 지키면 됨 |
| 학습 단계의 생성형 AI 사용 | ✅ | 금지 대상은 *"평가용 테스트 데이터의 예측 과정"* 에 한정(p.5, p.10) |
| 추론 시 전부 로컬 가중치 | ✅ 필수 | 네트워크 차단 상태 완주 검증(`01` §4) |
| 재현성 (축 B가 결정적인가) | ✅ | skeletonize·Hough·FFT·SAM 모두 결정적. 시드 고정만 하면 됨 |
| 계열 분류를 병렬 점수로 사용 | ✅ | 검색 기반 attribution을 배제했으므로 외부 조회 없음 |
| Ultralytics YOLO | ❌ 배제됨 | AGPL이 산출 가중치까지 적용 |
